# Story 2.2.1: n8n Workflow Orchestration for Document Processing

## Status

Approved

## Story

**As a** System Administrator and Operations Manager,
**I want** document processing workflows orchestrated through n8n,
**so that** I can monitor, configure, and scale document processing workflows visually without code changes, and leverage n8n's built-in retry logic, error handling, and workflow monitoring capabilities.

## Acceptance Criteria

1. n8n workflow created for document chunking analysis pipeline with all processing steps
2. Upload endpoint triggers n8n workflow via webhook POST request
3. Database tracks n8n workflow execution IDs for audit and monitoring
4. n8n UI provides visual workflow monitoring with execution history
5. Workflow includes retry logic for failed processing steps (3 retries with exponential backoff)
6. Workflow includes error handling branches for different failure scenarios
7. Workflow timeout configured (max 10 minutes per document)
8. Python backend services exposed as HTTP endpoints callable from n8n
9. n8n workflow stores chunks and embeddings in database via API calls
10. Status updates propagated from n8n back to knowledge_documents table
11. Documentation for n8n workflow setup, import, and configuration
12. Integration tests verify n8n workflow triggering and completion
13. Monitoring dashboard shows workflow execution metrics and failure rates
14. No regression in existing Python-based document processing (fallback option)
15. Environment configuration supports toggling between n8n and direct processing modes
16. Duplicate file detection using content hash (SHA256) prevents redundant processing
17. Document revision tracking with version numbering for updated files
18. Configuration options for duplicate handling strategy (skip, create_version, replace)
19. UI displays document versions with ability to view revision history
20. n8n workflow includes duplicate check node before processing

## Dev Notes

### Story Context

This story (2.2.1) addresses the **n8n workflow orchestration gap** identified in Quinn's QA review of Story 2.2. The gap analysis (Story 2.2, lines 1546-1883) documents that while Story 2.2's Dev Notes described n8n-orchestrated document processing, the actual implementation uses Python FastAPI BackgroundTasks.

**Why This Story Exists:**
- Original design called for n8n workflow orchestration (Story 2.2 Dev Notes, lines 418-441)
- MVP implementation used simpler Python backend approach (pragmatic decision)
- n8n integration deferred as **architectural enhancement**, not functional blocker
- This story implements the originally planned architecture for operational benefits

**Story 2.2 Status:** ✅ Done - MVP Complete (Python backend processing works well)
**Story 2.2.1 Goal:** Add n8n orchestration as enhancement without disrupting existing functionality

### n8n Workflow Architecture

**Document Processing Workflow (via n8n):**

```
User Uploads Document
    ↓
Python Backend: POST /api/knowledge/upload
    ↓
Trigger n8n Webhook: POST http://n8n:5678/webhook/document-processing
    Payload: { document_id, filename, mime_type, storage_path, file_content_base64 }
    ↓
[n8n Workflow Starts]
    ↓
Node 1: Webhook Trigger (receives upload event)
    ↓
Node 2: Extract Document Text
    → HTTP POST /api/n8n/extract-text
    → Python service: DocumentProcessor.extract_text()
    → Returns: { document_id, text_content }
    ↓
Node 3: Analyze Chunking Strategy
    → HTTP POST /api/n8n/analyze-chunking
    → Python service: ChunkingAnalyzer.analyze_document_for_chunking()
    → Returns: { document_id, chunking_strategy }
    ↓
Node 4: Chunk Document
    → HTTP POST /api/n8n/chunk-document
    → Python service: DocumentProcessor.chunk_text_intelligently()
    → Returns: { document_id, chunks[] }
    ↓
Node 5: Generate Embeddings
    → HTTP POST /api/n8n/generate-embeddings
    → Python service: EmbeddingService.generate_embeddings_batch()
    → Returns: { document_id, chunks_with_embeddings[] }
    ↓
Node 6: Store Chunks in Database
    → HTTP POST /api/n8n/store-chunks
    → Python service: Inserts into knowledge_document_chunks table
    → Returns: { document_id, stored_count }
    ↓
Node 7: Update Document Status (SUCCESS)
    → HTTP POST /api/n8n/update-status
    → Update knowledge_documents: status='COMPLETED', n8n_workflow_id=<execution_id>
    → Returns: { document_id, updated }
    ↓
[n8n Workflow Complete]
    ↓
User sees: Document Status = COMPLETED (via polling or real-time updates)
```

**Error Handling Flow:**

```
Any Node Fails
    ↓
Retry Logic: 3 attempts with exponential backoff (5s, 10s, 20s)
    ↓
If all retries fail:
    ↓
Branch to Error Handler Node
    ↓
HTTP POST /api/n8n/update-status
    Payload: { document_id, status: "FAILED", error: "..." }
    ↓
Update knowledge_documents table: status='FAILED', processing_error=<error_msg>
    ↓
User sees: Document Status = FAILED with error message
```

### Security Considerations

**n8n Webhook Security:**
- **Authentication:** Use Bearer token or API key for webhook calls
- **HTTPS:** Enable HTTPS for n8n webhooks in production
- **IP Whitelisting:** Restrict webhook access to internal Docker network
- **Payload Validation:** Validate webhook payload schema

**API Endpoint Security:**
- **Authentication:** Require Bearer token or n8n API key for all `/api/n8n/*` endpoints
- **Rate Limiting:** Limit requests to prevent DoS (e.g., 100 requests/minute)
- **Input Validation:** Validate all request parameters
- **Output Sanitization:** Sanitize error messages to prevent information leakage

**Database Security:**
- **Least Privilege:** n8n database credentials should have minimal permissions
- **Audit Logging:** Log all n8n workflow executions and status updates
- **Encryption:** Encrypt sensitive data in transit (TLS) and at rest

**Error Handling Security:**
- **Sanitize Error Messages:** Don't expose stack traces or internal paths
- **Redact Sensitive Data:** Remove API keys, passwords from error logs
- **Secure Logging:** Log errors to secure location with access controls

### Performance Considerations

**Workflow Performance:**
- **Parallel Nodes:** Use n8n parallel execution where possible
- **Timeout Configuration:** Set reasonable timeouts (10 min max)
- **Resource Limits:** Monitor n8n container resources (CPU, memory)

**API Endpoint Performance:**
- **Connection Pooling:** Reuse database connections (already implemented in Story 2.2)
- **Caching:** Cache chunking strategies for similar documents (future enhancement)
- **Async Processing:** All endpoints use async/await for non-blocking I/O

**Monitoring Performance:**
- **Pagination:** Limit execution history queries (max 100 records)
- **Caching:** Cache metrics for 30 seconds to reduce database load
- **Indexing:** Database indexes on n8n_workflow_id and n8n_execution_status

**Scaling Considerations:**
- **Horizontal Scaling:** n8n can run multiple workers for parallel execution
- **Queue Management:** n8n internal queue handles concurrent workflows
- **Database Connection Pool:** Ensure pool size supports n8n concurrency

### Risk Mitigation

**Risk 1: n8n Documentation Not Available**
- **Mitigation:** Agent 3 must check context7 response before proceeding
- **Fallback:** Use WebFetch to retrieve n8n documentation from official site
- **Impact:** May delay n8n workflow creation by 2-4 hours

**Risk 2: Phase 1 Agents Block Each Other**
- **Mitigation:** Ensure all Phase 1 agents launched in single message
- **Monitoring:** Check agent status every 30 minutes
- **Impact:** Could negate parallel benefits if launched sequentially

**Risk 3: Integration Test Failures**
- **Mitigation:** Each Phase 1 agent must pass unit tests before Phase 2
- **Rollback:** Phase 2 agent reports failures to relevant Phase 1 agents for fixes
- **Impact:** May require 1-2 hours of debugging and re-testing

**Risk 4: Docker Resource Exhaustion**
- **Mitigation:** Monitor Docker resources during parallel development
- **Limit:** Run max 6 agents simultaneously (Phase 1)
- **Impact:** If resources exhausted, reduce to 3-4 agents at a time
