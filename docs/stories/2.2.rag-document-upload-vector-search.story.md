# Story 2.2: RAG Document Upload & Vector Search Implementation

## Status
In Progress - Core Features Implemented (Document Upload, Vector Search)

## Story
**As a** Government Program Director or Knowledge Manager,
**I want** to upload documents to the knowledge base and perform semantic search using vector embeddings,
**so that** I can leverage RAG (Retrieval-Augmented Generation) to find relevant information and get AI-powered answers to questions based on my organization's documentation.

## Acceptance Criteria
1. Database schema supports vector embeddings storage with pgvector extension
2. Knowledge chunks table includes vector column with proper indexing for similarity search
3. Backend service can generate embeddings using Ollama or Google Gemini
4. API endpoint accepts document uploads (PDF, DOCX, TXT, MD, HTML)
5. Document processing pipeline extracts text, chunks content, and generates embeddings
6. Uploaded documents are stored in MinIO with metadata in database
7. Vector similarity search endpoint returns semantically relevant chunks
8. RAG query endpoint combines vector search with LLM to answer questions
9. Frontend UI provides document upload interface with progress indicators
10. Frontend UI provides semantic search interface with query input and results display
11. Embedding model health check endpoint verifies service availability
12. All document processing operations are tracked with status updates
13. Error handling for document processing failures with user-friendly messages
14. Integration tests verify complete upload-to-search workflow
15. No regression in existing Knowledge Management features

**Recommended: Ollama (Local LLM)**
- **Model:** nomic-embed-text (137M parameters, 768 dimensions)
- **Advantages:**
  - Already configured in project
  - No external API costs
  - Privacy-first (all data stays local)
  - Fast inference on local hardware
- **Ollama API Endpoint:** http://host.docker.internal:11434

**Alternative: Google Gemini**
- **Model:** text-embedding-004 (1536 dimensions)
- **Advantages:**
  - Higher quality embeddings
  - Faster processing for large batches
- **Considerations:** Requires API key, external dependency

**Decision:** Use Ollama as primary with Gemini as optional fallback

### Vector Index Strategy

**pgvector Index Types:**
1. **IVFFlat** (Inverted File Flat)
   - Good for datasets < 1M vectors
   - Faster index build time
   - Configurable lists parameter
   ```sql
   CREATE INDEX ON knowledge_chunks
   USING ivfflat (embedding vector_cosine_ops)
   WITH (lists = 100);
   ```

2. **HNSW** (Hierarchical Navigable Small World)
   - Better for datasets > 1M vectors
   - Higher search accuracy
   - Slower index build
   ```sql
   CREATE INDEX ON knowledge_chunks
   USING hnsw (embedding vector_cosine_ops)
   WITH (m = 16, ef_construction = 64);
   ```

**Decision:** Start with IVFFlat for MVP, migrate to HNSW if dataset grows

### Document Chunking Strategy **UPDATED: Intelligent LLM-Driven Approach**

**Intelligent Chunking Approach (LLM-Driven):**
- **Analysis Phase:** LLM analyzes each document to determine optimal chunking strategy
- **Thought Preservation:** Chunks are created at semantic boundaries to preserve complete thoughts
- **Adaptive Sizing:** Chunk size dynamically determined based on:
  - Document type (technical, narrative, structured data)
  - Content complexity (simple prose vs. dense technical content)
  - Structural elements (sections, paragraphs, code blocks, tables)
  - Semantic density (information-rich vs. conversational)
- **Context-Aware Overlap:** Overlap calculated to maintain continuity without redundancy
- **Special Handling:** LLM identifies special content requiring custom chunking:
  - Code blocks (preserve complete functions/classes)
  - Tables (keep complete tables together)
  - Lists (preserve list items with context)
  - Diagrams/Charts (keep descriptions together)

**LLM Chunking Analysis Process:**
```
Document Upload
    ↓
Extract Full Text
    ↓
Send to LLM: "Analyze this document and recommend chunking strategy"
    ↓
LLM Response: {
  recommended_chunk_size_range: [400, 800],
  semantic_boundaries: ["paragraph", "section"],
  overlap_tokens: 75,
  special_handling: {
    code_blocks: "preserve_complete",
    tables: "keep_together",
    lists: "preserve_with_context"
  },
  rationale: "Technical document with code examples..."
}
    ↓
Apply Intelligent Chunking
    ↓
Generate Embeddings per Chunk
```

**Fallback Strategy:**
- If LLM analysis fails: Use default strategy (600 tokens, 10% overlap)
- If document too large for LLM context: Analyze first 5000 tokens as sample
- If specialized content detected: Apply predefined rules for that content type

**LLM Prompt Template for Chunking Analysis:**
```
Analyze the following document and recommend an optimal chunking strategy for RAG embedding generation.

Document Type: [auto-detected]
Document Length: [X tokens]
Sample Content:
---
[First 2000 tokens of document]
---

Provide recommendations for:
1. Optimal chunk size range (min-max tokens)
2. Semantic boundaries to respect (sentences, paragraphs, sections)
3. Overlap strategy (% or fixed token count)
4. Special handling requirements for code, tables, lists, or other structured content
5. Brief rationale for your recommendations

Respond in JSON format.
```

### RAG Pipeline Architecture **UPDATED: Intelligent Processing**

**Document Upload & Processing Pipeline (via n8n):**
```
User Uploads Document
    ↓
Upload to MinIO + Create DB Record
    ↓
Trigger n8n Workflow: "Document Chunking Analysis Pipeline"
    ↓
[n8n] Extract Document Text (PDF/DOCX/TXT/MD/HTML)
    ↓
[n8n] Send Text Sample to LLM for Chunking Analysis
    ↓
[n8n] LLM Returns Chunking Strategy (size, boundaries, special handling)
    ↓
[n8n] Apply Intelligent Chunking Based on LLM Recommendations
    ↓
[n8n] Generate Embeddings for Each Chunk (Ollama: nomic-embed-text)
    ↓
[n8n] Store Chunks + Embeddings + Strategy Metadata in Database
    ↓
Update Document Status: COMPLETED
    ↓
Notify User (optional webhook/email)
```

**RAG Query Pipeline:**
```
User Query
    ↓
Generate Query Embedding (Ollama/Gemini)
    ↓
Vector Similarity Search (pgvector)
    ↓
Retrieve Top-K Chunks (k=5-10) with metadata
    ↓
Rerank by chunking strategy awareness (prioritize thought-complete chunks)
    ↓
Construct Context Prompt with citations
    ↓
Send to LLM (Ollama/Gemini)
    ↓
Stream Response with Source Citations
```

### API Specifications

#### Document Upload Endpoint
**POST /api/knowledge/documents/upload**
```typescript
Request: multipart/form-data
  - file: File (required)
  - metadata: {
      name?: string,
      description?: string,
      security_classification?: string,
      source_type?: string
    }

Response: {
  success: true,
  data: {
    document_id: string,
    filename: string,
    status: "PROCESSING",
    job_id: string
  }
}
```

#### Processing Status Endpoint
**GET /api/knowledge/documents/:id/status**
```typescript
Response: {
  success: true,
  data: {
    document_id: string,
    status: "PROCESSING" | "COMPLETED" | "FAILED",
    progress: number, // 0-100
    chunks_processed: number,
    total_chunks: number,
    error?: string
  }
}
```

#### Semantic Search Endpoint
**POST /api/knowledge/search/semantic**
```typescript
Request: {
  query: string,
  limit?: number, // default: 10
  threshold?: number, // default: 0.7
  filters?: {
    source_type?: string,
    security_classification?: string,
    date_range?: { start: string, end: string }
  }
}

Response: {
  success: true,
  data: {
    results: [
      {
        chunk_id: string,
        content: string,
        similarity_score: number,
        metadata: {
          document_name: string,
          page_number?: number,
          section_title?: string
        },
        document_id: string
      }
    ],
    query_embedding_time_ms: number,
    search_time_ms: number
  }
}
```

#### RAG Query Endpoint
**POST /api/knowledge/rag/query**
```typescript
Request: {
  query: string,
  max_chunks?: number, // default: 5
  model?: string, // default: from config
  temperature?: number, // default: 0.7
  stream?: boolean // default: false
}

Response: {
  success: true,
  data: {
    answer: string,
    sources: [
      {
        chunk_id: string,
        document_name: string,
        similarity_score: number,
        snippet: string
      }
    ],
    confidence: number,
    processing_time_ms: number
  }
}
```

#### RAG Query Streaming Endpoint
**POST /api/knowledge/rag/query/stream**
```typescript
Response: Server-Sent Events (SSE)
  - event: chunk
    data: { text: string }

  - event: source
    data: { chunk_id: string, document_name: string, similarity_score: number }

  - event: done
    data: { total_tokens: number, processing_time_ms: number }
```
